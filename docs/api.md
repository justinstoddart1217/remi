# Remi API

The contract the frontend builds against. It is generated from the Pydantic schemas in
`backend/app/schemas/` into `contracts/openapi.json` and `frontend/src/api/schema.d.ts`
(`make openapi`; `make openapi-check` fails on drift). `backend/tests/api/routes_table.py`
pins every route, so changing the contract means an ADR, an edit to that table and
`make openapi`.

Every route below is implemented. `create_app` calls `app/api/router.py:install_api(app,
config)`, which mounts the routes, the error envelope and the security middleware, and adds
`POST /api/dev/fixtures` only when `REMI_ENV` is `dev` or `test`. A 501 `NOT_IMPLEMENTED` now
only comes from an app built without its database (the unwired `tests/api` app); routes with
validated inputs resolve the database lazily (`api/deps.py:WiringDep`), so a bad request is
still a 422 there.

## Conventions

- **Base path:** everything is under `/api` on `127.0.0.1:8765`. There is no auth and no CORS.
- **Casing:** JSON keys, query parameters and path parameters are camelCase
  (`/projects/{projectId}?…`, `{"workLeft": 12}`). Enum *values* keep their own spelling:
  check-in change types are snake_case (`task_done`), charter lists are camelCase (`inScope`),
  rotation passes are `Build`/`Refresh`.
- **Dates:** business dates are ISO `YYYY-MM-DD` strings. Timestamps (`createdAt`,
  `updatedAt`, `nextRolloverAt`, …) are ISO-8601 with an offset. Maps keyed by date
  (`loads`, `dayHours`, `overrides`) use ISO keys.
- **Responses** declare every key; an empty value is `null`, never absent. The generated TS
  response types therefore have no optional keys.
- **Requests** reject unknown keys (422). In a `PATCH`, an absent key means "unchanged" and
  `null` means "clear" (e.g. `{"targetLabel": null}`).
- **Requests are strict about types** (`schemas/base.py:CamelIn`). A boolean must be `true` or
  `false` (`{"completed": "yes"}` and `{"completed": 1}` are 422s). An integer must be a JSON
  integer (`{"bd": true}`, `{"bd": "10"}` and `{"bd": 10.0}` are 422s), including the integer
  enums `phase` and `stage`. A number must be a JSON number (an integer is fine; `"1.5"` and
  `true` are not). A date must be exactly `YYYY-MM-DD` (no timestamps, no Unix numbers). The
  error is 422 `VALIDATION_ERROR` with `field` set, and nothing is written.
- **Ids** are opaque strings (UUIDs). Textbook block ids are generated by the client.
- **Errors** always use the envelope `{"error": {"code", "message", "field"}}` (`field` is the
  camelCase request field, or `null`). The catalogue is at the end of this page and in
  `app/schemas/errors.py`.
- **Setup gate:** until `POST /setup` has run, reads that need the move date (`/plan`, `/day`,
  `/month-snapshot`, `/loads`, projects, routines, rotation) answer 409 `SETUP_REQUIRED`.
  `/setup`, `/setup/countdown`, `/calendar`, `/home`, `/settings`, `/ai/status`, notes and
  the Textbook work before setup.

## Security (applies to every request)

- **Host:** only loopback names (`127.0.0.1`, `localhost`, `[::1]`) are served; anything else
  is a plain-text 400 "Invalid host header" (not the JSON envelope). This blocks DNS rebinding.
- **Mutations** (`POST`, `PUT`, `PATCH`, `DELETE` under `/api`) need both
  `Origin: http://127.0.0.1:8765` (or `localhost`, or the Vite dev port `REMI_WEB_PORT`,
  default 5173, outside prod) and
  `X-Remi-Client: 1`. Otherwise 403 `FORBIDDEN_ORIGIN` / `CLIENT_HEADER_REQUIRED`. The browser
  sends `Origin` itself; `frontend/src/api/client.ts` adds the header.
- **Headers:** every response carries `Content-Security-Policy` (`'self'` only; inline styles
  allowed for KaTeX), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and
  `Cross-Origin-Opener-Policy: same-origin`. Chart HTML (`GET /api/charts/{assetId}`) has its
  own CSP: `sandbox allow-scripts; default-src 'none'; connect-src 'none'; …`. Render it with
  `<iframe sandbox="allow-scripts" src="/api/charts/{assetId}">` (never `allow-same-origin`,
  never `srcdoc`).
- **500s:** an unhandled exception is answered with the `INTERNAL_ERROR` envelope from inside
  the security middleware (`UnexpectedErrorMiddleware`), so it carries the same headers.
- API keys are write-only (`PUT /settings/ai-key`); no response ever contains one.
  `PUT`/`DELETE /settings/ai-key` return `AiStatusOut`, not the plan: the key does not shape
  the plan, but `aiKeyConfigured` (in `GET /settings` and `PlanOut.settings`) changes. Set it
  from the returned `keySet` in the cached plan and settings, or invalidate both queries.

## Mutations return the plan

Every plan mutation returns `MutationOut`:

```ts
{ plan: PlanOut, movements: Movement[], entity?: … }   // entity is typed per route
Movement = { projectId, fromForecast, toForecast, deltaBd, fromTarget, toTarget,
             cause, label, flash, moved }
```

Replace the plan query data with `plan` in one commit, then play `movements`: after the drawer
closes wait 220 ms, `flash` (ghost bar) for 1100 ms, the `moved` chip (`label`, e.g. "+3 BD")
for 5200 ms. Deletes return `MutationOut` without `entity`. Textbook routes do not touch the
plan and return their own models.

`GET /plan` sends `ETag: "<revision>-<today>"`; send it back as `If-None-Match` to get a 304.
`PlanOut.today.nextRolloverAt` is when to refetch for a new day.

**The revision moves only with events that can change the plan.** It is the `seq` of the latest
event whose type is not in `PLAN_NEUTRAL_EVENTS` (`repositories/models/events.py`): note text
edits (`note.updated`) and Textbook edits (`textbook.blocks_saved`, page create and rename,
section create, update, reorder and delete, chart upload, delete and collection). The plan
never shows note text or Textbook content, so autosave while typing never invalidates the plan
or its ETag, and a note or Textbook write that returns a plan returns the same revision. Adding
or deleting a note does move it (`counts`), and so does deleting a Textbook page (it can
rewrite `settings.uiPrefs`). `tests/read/test_plan_revision.py` rebuilds the plan after every
neutral event and checks that nothing changed. The client should still store the `plan` a
mutation returns; when its `revision` is unchanged, there is nothing to refetch.

## Behaviour notes

Rules the route tables cannot show. Each is tested in `backend/tests/`.

### Hours and forecasts
- **Routine hours** (`PATCH /routines/{id}` `hours`) take any finite number from 0 and are
  clamped to the settings capacity, as the prototype's field is: `99` saves as `8` on an 8h day.
  A negative number, `Infinity` or `NaN` is a 422.
- **Project hours** (a rate, `rateAfterMove`, BAU-day hours, an override, a check-in
  `hours_per_day`) are 0 or from 0.05 to 24. A rate of 0 on a project with a forecast is 422
  `VALIDATION_FAILED`, "Hours a day must be more than 0 for a project with a forecast." (a
  zero rate never finishes; ADR-0007). Service messages are sentences, ready to show after
  "Couldn’t save that."
- **A rate change rescales the other figures** (`rateAfterMove`, BAU-day hours, overrides) by
  the same factor, so a valid rate can still push one of them past 24h or below 0.05h. Then
  `POST …/replan` and `…/replan/preview` are both 422 on `rate` ("That would plan some days at
  more than 24h. Use a smaller value."), and a check-in `hours_per_day` is 422 on
  `changes.N.value` in preview and apply alike. `validate()` drops such a proposal (and any
  `hours_per_day` below 0.05) from AI and simple readings, with the reason in `dropped`, so a
  proposal never fails the whole preview.
- **Edits that reshape the hours keep the work left.** A new move date or holiday region
  (`PATCH /settings`, cause `settings`), a holiday added or removed (cause `calendar`), a
  routine's rule, stage or domain changed or the routine removed (cause `routine`), and a
  project's BAU-day hours (cause `bau_day_hours`), overrides (cause `override`) or
  `rateAfterMove` (cause `rate`) change which days have how many hours without touching any
  work left. In the same transaction every stored forecast is placed again from the work left
  it had before the change, and the movements come back as usual. So an earlier move turns
  Private Credit hours past it into unplaced hours (not lost work), a later one places them
  again, and a forecast never stays on a day that lost its hours (ADR-0007's invariant: a
  `workLeft` replan with the project's own `derived.workLeft` changes nothing). As with a
  rate edit, the work left counts the forecast day in full, so it can grow by up to one day's
  hours. Leave and capacity change no project's hours, so they move no forecast.
- **Fixed Income carries on after the move.** A new project has no rates; a Fixed Income
  project's first rate or work left sets `rateAfterMove` to the same figure (a first work left
  plans 1h a day), and later rate edits scale it like the other figures. Private Credit keeps
  0h after the move. Unplaced hours, in either domain, make a project `risk` with the
  `after_move` sentence (`cutH` = the work to cut to finish before the move).
- **The verdict waits for every Private Credit plan.** While any Private Credit project is in
  Define (no forecast), the verdict is `no_pc` ("Move not planned yet"), not `on_track`: its
  exit is unknown. `bufferBd` and `lastPcExit` still describe the planned exits. An exit that
  already misses the move still makes it `off_track`.

### Routines
- **`label`** is the curated row label the Timeline shows (the design seed shortens
  "Fund & security-level returns" to "Fund & security returns"); `null` means show `name`. A
  `PATCH` with a blank or `null` `label` clears it. A rename clears it too, unless the same
  `PATCH` sends a `label` (the old label shortened the old name).
- **`short`** survives a rename when it was curated; a short that was blank or mirrored the old
  name follows the new name, and a blank `short` falls back to the name.
- **A new routine starts on the day it is created** (stored as `routines.starts_on`, not sent).
  Its runs before that day are not due, overdue or loaded, so a routine added mid-month does not
  show the month's earlier runs as overdue on Today or as chips on past Calendar days. Routines
  that existed before this rule take the day of their `routine.created` event; the design
  fixture's routines have always run. A rule edit does not move the start.

### Check-ins
- **The simple reading's blockers** need a blocker word (`waiting`, `blocked`, `stuck`) that
  starts a word and is not negated: "unblocked now", "no longer blocked by Finance" and "not
  stuck anymore" are notes, not blockers.

### Rotation
- **Loop 1** (`loopBd`, `loopEnd`) is the Build segments before the first Refresh; the fixture
  gives 46 BD ending Mon 8 Mar 2027 whatever comes after the refresh. `refresh` is the first
  run of Refresh segments.
- **The horizon is checked before anything is written.** `PUT /rotation/segments`,
  `PATCH /rotation {startDate}` and `POST /setup` with segments lay the rotation out first: on
  the plan's calendar, or, when that is too short, on the calendar up to ten years ahead built
  in memory. A rotation whose last day falls after 31 Dec of today's year + 10 is 422
  `OUT_OF_RANGE` (`field` `segments`), however far the stored calendar already reaches (it
  runs to the year after the move, so a late move can take it past the horizon), and records
  no event at all (not even a `holidays.generated`). One that fits is saved, and the
  stored calendar widens as far as it needs (`holidays.generated` events, then the change's
  own event).
- **Settings that move the rotation are checked the same way.** `PATCH /settings {moveDate}`
  moves a rotation that follows the move date (`startFollowsMove`), and `{holidayRegion}`
  moves any rotation's business days. When the rotation would then end past the horizon the
  patch is 422 `OUT_OF_RANGE` (`field` `moveDate` when a sent move date is what moves it,
  else `holidayRegion`) and records no event. A rotation with its own
  `startDate` does not follow the move, so a late move date is accepted for it.

### Calendar
- **Reads that widen the calendar store holiday years** only inside the read horizon (ten years
  either side of today's year) plus a year of slack, and record one `holidays.generated` event,
  which moves the plan revision (docs/requests/R-read.md). `GET /setup/countdown` follows the
  same rule: it answers any move date in 1990-2100 (a preview, although `PATCH /settings`
  refuses a move more than ten years out), and generates years past the horizon in memory.

### Textbook
- **Section labels.** `PATCH /textbook/sections/{id} {"label": "  "}` on an empty, unnamed
  section that is not the last one deletes it (the prototype's rename commit); the answer is
  the section as it was, and the tree no longer lists it. A blank label on a named section is
  ignored. Labels are trimmed.
- **Upload warnings.** `ChartUploadOut.warnings` holds one sentence when the HTML loads from the
  web, for example "yield.html loads from the web (fonts.googleapis.com). Charts run offline,
  so anything it fetches from there will be missing." `http(s)://` and protocol-relative
  `//host/…` references count (in quotes, `url(…)` or attribute values); JavaScript `//`
  comments and XML namespace URIs do not. The upload is still saved.
- **Chart garbage collection.** An asset no chart block uses is kept for a grace period of
  **1 hour** after its (latest) upload, so the editor can put a fresh `assetId` into a block on
  its next autosave. An asset that a save or page delete just stopped using goes at once, with
  its file, unless it was uploaded again after that page last saved its blocks (a rename does
  not count as a save). Uploads larger than 4 MB are 413.

### Notes
- **The rail** (`GET /notes/days` `rail`) lists the business days from today back 27 days, plus
  every day that has notes, future days included (the prototype showed only today and
  earlier; ADR-0007).
- Note writes return the plan, so they answer 409 `SETUP_REQUIRED` before setup. Editing a
  note's text does not move the plan revision (see "Mutations return the plan").

### Database
- **Backups.** Before a migration `remi` copies `remi.db` to
  `backups/remi-<revision>-<timestamp>.db` and keeps the newest 10 of those; `remi db backup`
  copies (`remi-manual-…`) are a separate pool of 10, so they never push out the pre-migration
  copy.
- **A database Remi cannot use** stops `remi` and `remi db upgrade|backup` with a plain message
  and exit status 1, not a traceback, and takes no backup: one written by a newer Remi (an
  unknown schema revision: "Update Remi, or restore a backup in …/backups") or a file that is
  not a readable SQLite database (move it aside for a fresh one, or copy a backup over it).
  Every directory Remi creates under the data directory is 0700, `charts/` included.

### Dev and test runs
- **`POST /dev/fixtures`** exists only with `REMI_ENV=dev|test`. `design` loads the prototype's
  sample data and returns the plan; `empty` resets to a database that still needs setup and
  answers 204. Both then sweep the chart files no row names any more, so `empty` leaves no
  chart on disk.
- **Environment pins.** `REMI_NOW` and `REMI_DEFAULT_TIMEZONE` are refused at startup with
  `REMI_ENV=prod`:
  - `REMI_TODAY=2026-10-05`: the business date starts on that day; the wall clock keeps running.
  - `REMI_NOW=2026-10-05T09:30:00+01:00` (dev and test only): the clock stands still at that
    aware instant, so note stamps, `createdAt` and every write's `updatedAt` are that instant
    (a second write to the same row keeps it too). It must fall on `REMI_TODAY` when both are
    set; alone, its own date is today.
  - `REMI_DEFAULT_TIMEZONE=Europe/London` (dev and test only): the zone `GET /setup` pre-fills
    instead of the machine's `/etc/localtime` (the holiday region follows it).
  - `REMI_WEB_PORT`: the Vite dev server's port, whose `Origin` passes the mutation guard
    outside prod (default 5173).

### `PlanOut` at a glance

| Key | Contents |
|---|---|
| `revision` | The latest plan-affecting event (not note text or Textbook edits); with `today`, the ETag. Never goes down. |
| `today` | `iso`, `tz`, `overridden` (`REMI_TODAY`), `w`, `isBd`, `bdm`, `monthBds`, `nextRolloverAt`. |
| `settings` | The full `SettingsOut` (move date, capacity, region, timezone, key project/routine, appearance, AI provider, `aiKeyConfigured`, UI prefs). |
| `calendar` | `from`, `to`, `region`, `days[{iso, w (0 = Sunday), bd, bdm, hol, week}]` from the Monday before today − 1 week to the latest of move + 2 weeks, the month after the move, the rotation end and the last project end. |
| `loads` | `{iso: {items[{refType, refId, domain, h, name}], bau, proj, total, free, capacity, over}}` for every business day in `calendar`. |
| `projects[]` | Stored fields, charter, milestones with tasks, readiness items, scope changes, risks and checklists (data only), `bauDayHours`, `overrides`, and `derived` (status, `deltaBd`, `planFrom`, `sinceDays`, `stale`, `addedH`, `growthPct`, `workLeft`, `workLeftDisplay`, `bdLeft`, `bdToTarget`, `totalBd`, `doneBd`, `progressPct`, `need{rate, state}`, `avgPlan`, `bufferBd`, `absorbH`, `cutH`, `cutBeforeMoveH`, `landsAfterMove`, `startsInBd`, `overDays`, `nowEstimateH`, `readinessPct`, `sentence{case, params}`, `milestones`, `nextMilestone`, `dayHours`). |
| `routines[]` | Stored fields (including `label`, the curated Timeline row label, `null` = show `name`), `rule{kind, bd, weekday}`, `checklistItems`, and `derived` (`next` 3 occurrences, `occurrences` in the calendar window, `monthlyEffortH`, `runsToday`, `countsToday`, `todayRun`, `lastBeforeMove`, `handedOver`). |
| `rotation` | Title, effective start, `hoursPerDay`, `segments[{order, country, code, lengthBd, pass, loop, start, end}]`, `loopBd` and `loopEnd` (loop 1: the Build segments before the first Refresh, so a Build pass after the refresh does not count), `refresh` (the first run of Refresh segments), `totalBd`, `current{status, order, bdToStart}`. Always present after setup; may have no segments. |
| `move` | `date`, `countdownBd` (strictly between today and the move: 61 in the fixture), `remaining[{iso, bdm, pcRunning}]`, `flags[{kind, projectId, iso, atRisk}]`. |
| `verdict` | `state` (`off_track`, `at_risk`, `on_track_narrowly`, `on_track`, `no_pc`: no Private Credit project, or one still in Define), `bufferBd`, `lastPcExit`, `keyProjectId`, `keyRun`, `toRunBd`, `anyRisk`. |
| `flags` | Data only: `upcomingOverloads`, `attention`, `promptProjectId`, `nextDueProjectId`. |
| `aliases` | Stored aliases. Names and short names always match too. |
| `counts` | `projects`, `routines`, `notesTotal`, `noteDays`, `notesToday`, `recentNotes`. |

The Workspace verdict sentence is `derived.sentence.case` (`no_plan`, `after_move`, `late`,
`no_buffer`, `buffer`) with its numbers in `params`; the appended clauses come from
`params.overDayCount`/`firstOverDay`, `staleDays` and `startsInBd`.

## Error codes

| Code | Status | Meaning |
|---|---|---|
| `VALIDATION_ERROR` | 422 | A request field failed schema validation; `field` names it (`null` when the body as a whole is wrong: malformed JSON, missing, or not an object) |
| `VALIDATION_FAILED` | 422 | A service rejected a value (domain rule); `field` names it |
| `NOT_FOUND` | 404 | Unknown `/api` path or entity id |
| `METHOD_NOT_ALLOWED` | 405 | The path exists but not with this method |
| `NOT_IMPLEMENTED` | 501 | The app has no database wired in (only the unwired test app) |
| `SETUP_REQUIRED` | 409 | First-run setup is not complete, so there is no move date yet |
| `SETUP_ALREADY_DONE` | 409 | `POST /setup` after setup completed (use `PATCH /settings`) |
| `CONFLICT` | 409 | Generic state conflict |
| `DOMAIN_ERROR` | 400 | Generic domain failure (a `DomainError` without a specific code) |
| `VERSION_CONFLICT` | 409 | Textbook `baseVersion` is stale; refetch the page |
| `SECTION_NOT_EMPTY` | 409 | Only empty textbook sections can be deleted |
| `LAST_SECTION` | 409 | The last textbook section cannot be deleted |
| `NOT_AN_OCCURRENCE` | 422 | The routine does not run on that date |
| `RUN_NOT_EDITABLE` | 409 | Checklist ticks are only editable for today's run |
| `OUT_OF_RANGE` | 422 | A date is outside the supported calendar (1990 to 2100) or more than ten years from today's year; also a rotation that would run past that horizon (`field` `segments`, or `moveDate`/`holidayRegion` from `PATCH /settings`) |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | Chart uploads must be .html/.htm UTF-8 text |
| `PAYLOAD_TOO_LARGE` | 413 | Chart upload over the size limit (4 MB) |
| `AI_NOT_CONFIGURED` | 409 | The chosen provider has no key, SDK or reachable Ollama |
| `AI_AUTH` | 502 | The provider rejected the key |
| `AI_BAD_REPLY` | 502 | The provider replied without a usable proposal |
| `AI_UNAVAILABLE` | 502 | The provider could not be reached |
| `AI_RATE_LIMITED` | 503 | The provider is rate limiting |
| `AI_TIMEOUT` | 504 | The provider did not answer in time |
| `PARSE_CANCELLED` | 409 | The parse was cancelled (`DELETE /checkins/parse/{parseId}`) |
| `FORBIDDEN_ORIGIN` | 403 | Mutating call without an `Origin` Remi answers to (loopback on its port, or `REMI_PUBLIC_URL`'s origin behind a proxy) |
| `CLIENT_HEADER_REQUIRED` | 403 | Mutating call without `X-Remi-Client: 1` |
| `INTERNAL_ERROR` | 500 | Unexpected server error; details are only in the server log |
